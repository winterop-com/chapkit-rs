# AGENTS.md

Instructions for AI coding agents working in this repository. `CLAUDE.md` is a symlink to this file.

## What this is

chapkit-rs is an experimental Rust take on [chapkit](https://github.com/dhis2-chap/chapkit): a library for
serving forecasting models to Chap. Models are Rust trait implementations called **in-process**; there is no
shell runner (use Python chapkit for R/Python/shell models). The public HTTP API must stay compatible with
Python chapkit so chap-core and chap-marketplace work unchanged; internals (storage, artifacts) may differ.

The point is speed: explainers (LIME/SHAP), HPO and AutoML call a model thousands of times, which only works
when a call is a plain function call, not a 2-3 s job round trip.

## Layout

- `crates/chapkit-dataframe`: columnar `DataFrame` with the chapkit `{columns, data, schema?}` wire format.
- `crates/chapkit-core`: pure model contract (no IO, no async): `Model` trait, `RunInfo`, `ModelInfo`,
  `SearchSpace` (chap-core format), `Period`, `prediction_frame`, safetensors `Checkpoint` + `Provenance`.
- `crates/chapkit-http`: HTTP plumbing with no model knowledge: problem+json errors, job scheduler,
  health, system, info, API keys, request ids, orchestrator registration, OpenAPI.
- `crates/chapkit-store`: async `Store` trait and its SQLite backend (rusqlite); no HTTP.
- `crates/chapkit-flow`: chap-core's flow as a test against a running service over HTTP; used by `chapkit-rs test`
  and every model binary's `test` subcommand.
- `crates/chapkit-cli`: the `chapkit-rs` command: `init` (scaffold a model package from `templates/`) and `test`
  (chap-core's flow against a running service). `init` copies `docker/Dockerfile`, so keep the templates working
  with it; CI scaffolds a package and runs it on every push.
- `docker/`: the shared Dockerfile for every model package (see the book's Docker guide).
- root package `chapkit`: the crate users depend on. `Service` turns a `Model` into the full
  chapkit-compatible API; re-exports the crates above.
- `tests/contract.rs`: the chapkit HTTP contract end to end, with a tiny model defined in the test.
- Model packages live in the sibling repository `../chapkit-rs-models` (chap-core baseline ports with
  parity tests). They depend on this library by path; update them with every library change and run
  `make models-check`.
  Their images are built against this repository's `main` but published once per models version (the
  `version` in chapkit-rs-models' `Cargo.toml`; chap-core treats a model version as write-once). A library
  change the models should ship reaches their images only with a version bump there.

## Workflow

1. Run `make lint` and `make test` after every change. Clippy warnings are errors.
2. Be concise. Only add code related to the task; skip nice-to-have extras.
3. If the prompt is unclear, ask follow-up questions until you are confident you can solve the problem.

## Git and pull requests

1. Use Conventional Commits for commit messages and PR titles.
2. Name branches after the commit prefix: `feat/`, `fix/`, `docs/`, `refactor/`, etc.
3. No attribution lines in commits or PRs (no `Co-Authored-By`, no `Generated by`).
4. No emojis anywhere: commits, PRs, code, comments, docs.

## Rust rules

1. No `unwrap()`, `expect()`, `panic!`, `todo!` or `unimplemented!` in library or example code; clippy denies
   them. Return `Result` instead. Tests may unwrap.
2. Avoid indexing that can go out of range on caller-supplied data; use `get()` and return an error.
3. `chapkit-core` stays pure: no IO, async, HTTP or database dependencies.
4. Model `Config` types must accept unknown fields (no `deny_unknown_fields`); configs also carry chapkit's
   reserved keys such as `prediction_periods`.
5. Measure performance claims with `make bench` (criterion), not by eye.

## Tests

1. Add a test for every new feature or fix.
2. HTTP behaviour that chap-core relies on is pinned in `tests/contract.rs`; keep it passing and extend it
   when the API changes.
